A few words I use a lot: a *block* is 32 bytes (8 ints) in the Part B cache, the *set* is which of the 32 cache slots an address lands in, and two rows *collide* when they land in the same set, so loading one kicks the other out.

## Part A: the simulator

### How I store the cache

The cache is one big `calloc`'d array of `S * E` structs. Each has a valid flag, a 64-bit tag, a dirty flag and a `last_used` number. Set `i` owns entries `i*E` to `i*E + E - 1`. One array works for any `s`, `E` and `b`, and `calloc` zeroes everything, so all lines start invalid for free.

Splitting an address takes two shifts and a mask:

- `set = (addr >> b) & (2^s - 1)`
- `tag = addr >> (s + b)`

Edge cases come free: with `s = 0` the mask is 0, so everything goes to set 0 (fully associative), and with `b = 0` the shift does nothing.

One address from `wb.trace` with `s = 1, b = 2`: `L 14,4`. `0x14` is `10100` in binary. The last 2 bits (`00`) are the offset, the next bit (`1`) is the set, and the rest (`10`) is tag 2. Set 1 is holding the block of `0xc` (tag 1), which went dirty on `S c,4`. So this load misses, kicks out a dirty line, and adds 4 bytes of writeback. Both simulators print `L 14,4 miss eviction writeback`.

### LRU and dirty lines

One counter goes up on every access and gets copied into `last_used` when a line is hit or filled. On a miss I use an empty line if there is one, otherwise I evict the line with the smallest `last_used`, i.e. the one used longest ago. I just scan the set's `E` lines (at most 8).

A store hit sets `dirty = 1`, and a new line is dirty only if a store brought it in. Evicting a dirty line adds `B` to `dirty_bytes_evicted`, and at the end one pass adds `B` for every line still dirty. An `M` is just a load then a store, so the store part always hits.

## Part B: the transpose

A and B both start in set 0. `A[i][j]` is at byte `4*(M*i + j)`, so its set is `floor((M*i + j) / 8) mod 32`, and B is the same with N instead of M. All numbers below are from my own `./test-trans` runs.

### 48 x 48

**Arithmetic.** A row of A or B is 48 * 4 = 192 bytes (6 blocks), so row `i` starts in set `6i mod 32`. Rows `k` apart collide when `6k` is a multiple of 32, which first happens at `k = 16` (rows 0, 16, 32 collide). Any 8 rows in a row land in 8 different sets (0, 6, 12, 18, 24, 30, 4, 10), so an 8x8 tile of one matrix is fine on its own.

The trouble is A against B. In a tile at A rows `8u..8u+7` and columns `8v..8v+7`, A row `8u+r` is in set `16u + 6r + v` and B row `8v+c` is in set `16v + 6c + u` (mod 32). On a diagonal tile (`u = v`) those match exactly when `r = c`, so A row r and B row r fight over one set.

| Strategy | Misses |
|---|---|
| Simple row-wise (handout) | 2664 |
| Blocked 4x4 | 1054 |
| Blocked 16x16 | 836 |
| Blocked 8x8, one element at a time | 778 |
| Quadrant scheme from the 48x64 case | 696 |
| **8x8 tiles, A row copied through 8 locals (final)** | **648** |

**Why it works, and the diagonal.** Plain 8x8 blocking reads one `A[i][j]`, writes one `B[j][i]`, and repeats, which turns into ping-pong on a diagonal tile. From `trace.f3`:

```
L 111000,4 miss eviction             A[0][0]: A row 0 loaded into set 0
S 151000,4 miss eviction             B[0][0]: B row 0 kicks it out, same set
L 111004,4 miss eviction writeback   A[0][1]: A row 0 again, kicks out dirty B row 0
```

That's 37 misses per diagonal tile versus about 18 elsewhere. My fix: read the whole A row into 8 locals first, then write it to B. Locals live on the stack, which isn't traced, so they're free, and when a B write kicks out the A line I'm already done with it. By hand, a diagonal tile costs 9 misses for the first row (1 A line, 8 B lines), then 2 per row after (the A row kicks out its partner B row and the write brings it back): 9 + 7 * 2 = 23. My per-tile breakdown showed exactly 23 on all six diagonal tiles. 648 is 72 above the best possible, 576.

### 48 x 64 (A is 64 rows by 48 columns)

**Arithmetic.** A rows are 192 bytes again (collide every 16 rows). But a B row is 64 * 4 = 256 bytes, exactly a quarter of the cache, so B row `j` starts in set `8j mod 32` and **B rows 4 apart collide**. 8 rows of B only get 4 sets to share.

| Strategy | Misses |
|---|---|
| Simple row-wise (handout) | 3544 |
| Blocked 8x8 | 3544 |
| Blocked 16x16 | 3544 |
| 8x8 tiles through 8 locals | 3460 |
| Blocked 4x4 | 1378 |
| Bands of 8 rows, column by column | 1015 |
| Quadrants v1 | 928 |
| **Quadrants v2 (final)** | **878** |

**Why it works.** Still 8x8 tiles, but done in 4x4 quarters, so I only write to 4 B rows (one per set) at a time:

1. Read A rows 0 to 3 whole into 8 locals. The left 4 values go straight to B rows 0 to 3; the right 4 get parked, already flipped, in the top-right quarter of those rows, which gets overwritten later anyway.
2. For k = 0 to 3: read column k of A's bottom-left quarter, grab the parked values from B row k, write the A column into B row k (finishing it), then put the parked values into B row 4+k. That row shares row k's set, but row k is done by then.
3. The bottom-right 4x4 goes into B rows 4 to 7, still in the cache.

v1 read the parked B row before the A column in step 2, and the A loads sometimes kicked out the B line I was about to write. Swapping that, and doing step 3 one B row at a time, got 878 (best possible is 768).

### 59 x 73 (A is 73 rows by 59 columns)

**Arithmetic.** A rows are 59 * 4 = 236 bytes and B rows 73 * 4 = 292 bytes, neither a multiple of 32, so no rows line up perfectly. Some come close: 13 * 236 = 3068 is 4 bytes short of 3 * 1024, so A row `i+13` collides with row `i` for most columns, and 7 * 292 = 2044 is 4 short of 2 * 1024, so B rows 7 apart nearly collide.

| Strategy | Misses |
|---|---|
| Simple row-wise (handout) | 4875 |
| Blocked 16x16 | 4645 |
| Blocked 8x8 | 2741 |
| Blocked 4x4 / column strips 4 wide | 2382 |
| Bands of 8 rows, column by column | 2055 |
| **Bands of 13 rows, column by column (final)** | **1928** |

**Why it works.** I take 13 rows of A and go through them one column at a time. 13 is the biggest band with no colliding rows, so all 13 A lines stay cached and get reused for the next few columns. Each column of the band becomes 13 ints in a row of B, filling B lines in one go.

**3. 48x64: blocking did nothing.** 8x8 and 16x16 both gave 3544, the same as the simple version. That confused me until the math showed B rows 4 apart collide. Quarters got 928, still just over 900.

**4. 48x64: the last 28 misses.** Trying reorderings through valgrind was slow, so I wrote a small Python model of the cache (always off from `test-trans` by exactly the 4 harness accesses). With it I found the step 2 swap in minutes.

**5. 59x73: square tiles went nowhere.** Best square was 4x4 at 2382, and 16x16 gave 4645 because a 16-row tile has rows 13 apart in it. So I had the model try every shape from 1x1 to 32x32. 13-row bands won, and it made sense afterwards: 13 is exactly where A rows start colliding.

Looking back, every fix came the same way: stop guessing tile sizes, work out which rows collide, and pick a shape that avoids it.
